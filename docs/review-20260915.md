## 2. 用探针找出的真实缺陷（已修）

### 缺陷 1：持续拒卡时**无限建卡**（严重）
- **怎么发现的**：探针注入"PATCH 持续失败" → 日志显示 `om_1 → om_15`，**15 次失败建了 15 张卡**。
- **根因**：`_flush_locked` 的失败路径是"封旧卡 → 建新卡"。飞书若持续拒卡，
  就变成"每条消息冒一张新卡"——**在用户屏幕上就是不停重复发东西**（与 football2 那次
  容量循环同一类病，只是触发源从"容量判定"换成"持续失败"）。
- **第一版修复无效**：我给计数器加了上限，但 `_create_locked` 成功时把 `failures` 归零了，
  于是"失败→换卡→建卡成功→计数清零"永远累积不到上限。**探针第二次跑就打脸（仍建 15 张）**。
- **最终修法（两层）**：
  1. `failures` 语义收紧为**连续 PATCH 失败**，只在**成功 PATCH** 时归零（建卡成功不归零）；
  2. 加**换卡配额**：单会话换卡次数 ≤ `max(3, 写入次数 // 5)` —— 因为"成功/失败交替"时
     连续计数会被成功那次清零，只有配额能兜住频率。
- **验证**：15 次连续失败 → 建卡 **3 张**（原 15）；30 次交替失败 → 建卡 **4 张**（原 16）。

### 缺陷 2：容量换卡**没有总量兜底**
- `MAX_ROTATIONS=50` 是硬上限，但容量换卡本身不检查配额 → 若容量判定失效（字段异常/边界），
  仍可能长时间刷卡。已让容量换卡**同样受配额约束**：超配额时不再换卡，继续写当前卡
  （出站前有元素折叠兜底，不会整卡被拒）。

## 3. 探针覆盖的不变量（全部通过）

`tests/probe_invariants.py` 穷举 594 条操作序列（长度 1-3 的全体组合 + 10 条压力序列），
每步检查：

| ID | 不变量 | 含义 |
|---|---|---|
| I0 | 无异常外抛 | 状态机任何输入都不能把异常抛给框架（会打断整轮回复） |
| I1 | 无换卡爆炸 | 换卡次数受控 |
| I2 | 建卡有界 | 建卡次数不随失败次数线性增长 |
| I3 | 内容不丢 | 换卡/心跳/收尾都不会让正文无故消失 |
| I4 | 卡片不越界 | 任何出站 payload 都不会"一出生就超限" |
| I5 | 计数自洽 | `append_count` 不为负、不虚高 |
| I6 | 状态合法 | `status ∈ {running, typing, sealed}` |
| I8 | 换卡收敛 | 建卡数 ≤ 配额（**这条抓出了上面两个缺陷**） |
| I9 | 换卡硬上限 | `rotations ≤ MAX_ROTATIONS` |
| I10 | 有内容必有 I/O | 不允许"静默不写" |

## 4. 上游契约核对（0.21.0 → 0.21.3）

完整核对 14 项依赖，**13 项签名与语义未变**；唯一破坏性变更：

| 变化 | 影响 | 我们的处境 |
|---|---|---|
| `send_exec_approval` 从 `FeishuAdapter` **上移到 `BasePlatformAdapter`**（飞书改覆写 `_send_exec_approval_prompt`） | 子类若直接 `super().send_exec_approval()` 仍可用（签名逐字一致），但**覆写点从公共方法变成了私有方法** | ✅ 插件用 `*args/**kwargs` 透传，仍工作；⚠️ 上游**没打任何 deprecated 标记**，属于静默重构 |
| 附加语义收窄 | `smart_denied=True` 或 `allow_session=False` 时**不再出现 "Always" 按钮**（旧版会） | 不影响插件（我们不做按钮集合断言） |
| `truncate_message` 实现重写 | 分块边界可能与 0.21.0 不同 → 长回复的卡片分块粒度变化 | 需长 markdown 实测 |

**上游没有任何"定制出站"的官方扩展点**（`register_platform` 签名未变、`PlatformEntry` 零新增字段、
`VALID_HOOKS` 无出站/卡片类钩子）⇒ 本插件的做法（同名平台覆盖 + 继承官方 adapter）
**是当前唯一可行路径，且上游不给稳定性承诺**。

## 5. 剩余的结构性风险（**这才是"别再打补丁"的关键**）

| # | 风险 | 现状 | 说明 |
|---|---|---|---|
| R1 | **依赖上游私有方法** | 7 处：`_feishu_send_with_retry` / `_finalize_send_result` / `_build_outbound_payload` / `_run_blocking` / `_client` / `_load_settings` / 模块级 `check_feishu_requirements` 等 | 上游本次已重构过其中 1 个（`_build_lark_client` 改委托）。下次改名/改签名 → **运行时静默 TypeError**，又是一轮"打补丁" |
| R2 | **每次 `hermes update` 都要人工重新验证** | 本次 update 后：更新改了 adapter（6088→4308 行）+ 停了 3 个网关 | 需要用"契约探针"把 R1 变成**自动检测**（已具备条件：`smoke_live.py --no-send` 就是在跑真实继承链） |
| R3 | **失败处理策略是"猜"** | PATCH 失败一律"换卡" | 失败原因分不清（限流/卡片被删/内容非法/网络）→ 用统一策略兜（配额）。更细的分层（按错误码分流）投入产出比不高，**当前配额方案足够** |
| R4 | **无结构化观测** | 卡片动作只有文本日志 | 出问题仍要人肉翻日志。建议：把 `[feishu-card]` 关键事件（create/rotate/seal/fail）计数暴露给 watchdog |
| R5 | **卡片内容上限是"多维约束"** | 元素 40 / 块 60 / 字节 15000 / 表格 2 / 追加 30 | 5 个维度各自有阈值，够用但难记忆。已统一收敛在 `card_render.py` 顶部常量 |
